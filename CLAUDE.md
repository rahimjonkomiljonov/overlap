# Overlap: campus dating app

Build it step by step from `docs/BUILD_PLAN.md`. The full product spec is `docs/REQUIREMENTS.md`.

## Working protocol

- At the start of a session, read `docs/BUILD_PLAN.md`, find the first unchecked step (`- [ ]`) and do only that step.
- Before coding a step, fetch current docs with Context7 for every library it touches. For Next.js 16 also read the matching guide in `node_modules/next/dist/docs/`.
- A step is done only when every "Done when" check passes. Then tick its box, add a line to the Progress Log in `docs/BUILD_PLAN.md`, and commit as `Sxx: title`.
- Stop at checkpoints C1 to C4 and wait for the owner's review.
- Build only what is in the Month-1 scope map. New ideas go to the Fast-follow list. Split any step that runs past 1.5x its budget.

## Hard rules (privacy and safety)

- **Local-only phase (standing, until the owner says "publish"):** no domain purchase, no Vercel/production deploy, no real email or SMS sending, no Sentry, no signing up new paid services. Build and test against `localhost` only. This overrides any build-plan step that assumes those exist (e.g. S04's email step falls back to logging OTP codes to the server console when `RESEND_API_KEY` is unset). Lift this only when the owner explicitly says to publish/deploy/go live — not implied by finishing a step.
- Never commit secrets. Keys live in `.env.local`; `.env.example` lists names only.
- Never store resident registration numbers. Never log, track or send to a third party: `interested_in`, selfies, chat text.
- Every server action and route handler checks authorization itself; the proxy only routes locales.
- Synthetic users exist only in dev and staging.

## Gotchas (learned the hard way)

- Every page and layout calls `setRequestLocale(locale)` before next-intl server APIs so it stays static. `loading.tsx` cannot, so anything it renders that uses next-intl must be a client component, otherwise the whole route becomes dynamic.
- Korean uses system fonts; only the Latin Pretendard slice is self-hosted (`src/app/fonts/README.md`). Do not add the Hangul webfont slices.
- Windows: never `taskkill /IM <image>`, it kills the owner's own programs (this closed their Chrome once). Stop only PIDs you started yourself. If `.next` is locked (`EBUSY`), find what holds it first.
- Lighthouse: set `CHROME_PATH` to Playwright's Chromium and use `C:/...` style paths for Node on Windows.
- Auth is Better Auth (`src/server/auth/auth.ts`), not Supabase Auth — Supabase Auth's default email sending doesn't fit local-only phase (see BUILD_PLAN S05 log for the full reasoning). The `NEXT_PUBLIC_SUPABASE_*`/`SUPABASE_SECRET_KEY` env vars are for Storage (S07 photos), unrelated to auth — and Storage itself follows the same local-only fallback as email (see below), so those vars stay unset until "publish" too.
- Photo/file storage (`src/server/storage/photos.ts`, S07) follows `sendEmail()`'s local-only-phase pattern: real Supabase Storage when `NEXT_PUBLIC_SUPABASE_URL`/`SUPABASE_SECRET_KEY` are set, otherwise a local `.dev-storage/` dir (gitignored) served through a guarded route that 404s once Storage is configured. CI has no Storage credentials either, so this fallback is what CI's own e2e run exercises — treat it as a real code path, not just an offline convenience.
- The `(app)` layout guard (S05, extended in S07 to also require a completed profile) redirects signed-out visitors to `/login`, not-yet-account-onboarded ones to `/onboarding`, and account-onboarded-but-profile-incomplete ones to `/onboarding/profile`. **Adding or changing any guard like this: audit existing e2e tests on the newly-protected routes.** They don't fail loudly — they silently keep "passing" while actually testing the redirect target instead (S05 found `shell.spec.ts`/`a11y.spec.ts` doing exactly this; S07 found it again when the profile-completion guard silently broke `signInAndOnboard()`'s promise to land on `/picks`). Use `signInAndOnboard()` from `e2e/helpers/auth.ts` for tests that need an authenticated, fully-onboarded session (it drives both onboarding stages), and add a `toBe(N)` / `toBeGreaterThan(0)` count guard before any loop over a locator, so an empty match can't pass silently.
- A file with `"use server"` at the top may only export async functions — no plain `const`/object/type-as-value export. This is enforced by the bundler at module-evaluation time, not by `tsc` or `next build`'s type-check step, so a violation compiles clean and only breaks when a page actually renders that module (S07: exporting a step-order lookup object from `src/server/profile/actions.ts` passed every check except real e2e). Put shared constants in a plain (non-`"use server"`) module instead.
- Playwright's `.count()` (and other synchronous-read locator queries) does **not** auto-wait the way `.click()`/`.check()`/`.fill()` do — it reads the DOM immediately. Calling it right after an action that triggers an async transition (a server-action round trip, a step change) can read the *previous* screen's state. Wait for an explicit signal of the new screen first (e.g. `expect(page.getByRole("heading", {...})).toBeVisible()`) before counting or querying (S07's `completeProfileWizard` e2e helper hit this: counting `fieldset`s right after clicking "다음" read 0 from the still-rendering previous step and silently skipped every check).
- Prisma 7 requires a driver adapter for every DB (`@prisma/adapter-pg`) and loads no env file on its own — `prisma.config.ts` loads `.env.local` explicitly. Use `process.env.X` directly there, never `prisma/config`'s `env()` helper: it throws immediately if unset, which breaks `prisma generate` (it needs no DB connection at all) on every clean install, including CI's and Vercel's.
- `prisma migrate dev` does not run `prisma generate` automatically in Prisma 7 — run it explicitly after every schema change or the generated client silently goes stale (wrong fields, confusing type errors). It also refuses to run at all (even with `--create-only`) in a non-interactive shell: use `prisma migrate diff --from-config-datasource --to-schema=prisma/schema.prisma --script` to get the SQL, hand-place it under `prisma/migrations/<timestamp>_name/migration.sql`, then `prisma migrate deploy` to apply and record it.
- No real campus data exists yet (O4). `prisma/seed.ts` creates a dev-only Campus + `test.ac.kr` EmailDomain for local/CI testing; it refuses to run when `NODE_ENV=production`.
- If you edit server code (actions, `sendEmail`, etc.) after already starting `npm run build`/`npm run start`, the running server is still serving the old build — rebuild and restart before trusting any test result. A test that fails for a suspiciously infrastructural reason (missing file, stale behavior) is worth checking against a fresh build before assuming it's a logic bug.
- CI uses its own throwaway `postgres:17-alpine` service (see `.github/workflows/ci.yml`), never the real Seoul database — don't add real DB credentials as GitHub secrets. New required env vars need a matching dummy (non-secret) value added to the CI workflow's `env:` block, or CI breaks even though local `.env.local` works fine.
- The dev/CI shell can have **real Seoul Supabase `DATABASE_URL`/`DIRECT_URL`** ambient in its environment (pointed at `aws-0-ap-northeast-2.pooler.supabase.com`), not just the `NEXT_PUBLIC_SUPABASE_*`/`SUPABASE_SECRET_KEY`/`SUPABASE_JWKS_URL` vars covered above — and since real process env always beats `.env.local`, `npm run dev`/`npm run e2e` silently talk to the real remote pooler instead of the local throwaway Postgres if only the Storage-related vars are unset. This doesn't fail loudly: pages still render, but every DB query (starting with the login OTP request) hangs for a few seconds and then fails with `pg-pool`'s "Connection terminated due to connection timeout" (the remote pooler is unreachable/too slow from here) — which looks exactly like a flaky signed-in e2e test, not an env problem, and can eat a lot of debugging time chasing the wrong cause (S13 lost real time to this before finding it: a plain `node -e` script using a hardcoded local connection string worked instantly, which is what revealed that only the *app's* connection was going elsewhere). For `npm run dev`, unsetting `DATABASE_URL`/`DIRECT_URL` is enough — `next dev` loads `.env.local` itself and fills them back in with the local value. For `npm run e2e`/`npx playwright test`, **export the local value instead of unsetting it** (`export DATABASE_URL=... DIRECT_URL=...`, both `postgresql://postgres:postgres@localhost:5432/postgres` in dev): the Playwright test-runner process itself (not just the `next dev` child it spawns) reads `process.env.DATABASE_URL` directly in `e2e/helpers/db.ts`'s own `pg.Pool`, and unlike `next dev` it does no `.env.local` loading of its own — leaving the var merely unset makes every `db.ts` helper call (`promoteToRole`, `verifyUser`, …) fail with pg's unrelated-looking "no PostgreSQL user name specified in startup packet".
- `src/server/env.ts` validates required env vars up front and is imported by `auth.ts` specifically so a missing `BETTER_AUTH_SECRET` fails the build instead of silently falling back to Better Auth's insecure default (which only warns). Import it from any other module that would otherwise fail unclearly on a missing var.
- A design-token pairing like `text-warning-foreground` is calibrated for a _solid_ `bg-warning`; pairing it with a low-opacity tint (`bg-warning/10`) can fail contrast in dark mode even though light mode looks fine. Use `text-foreground` (or `text-warning` for accents only) on tinted/subtle variants — see `src/components/draft-notice.tsx`.
- `messages/{ko,en}.json` values are constrained to `string | string[] | Tree` (`src/i18n/messages.test.ts`'s own type, which also asserts ko/en have identical key sets and no empty strings) — an array of objects (e.g. a table's rows as `[{heading, body}, ...]`) fails that type check at `tsc` time, even though `t.raw()` would happily return it at runtime. For structured content (S13's Terms/Privacy sections and tables), use a keyed object of objects instead (`{ purpose: {heading, body}, eligibility: {...} }`) and `Object.values()` it in the page — this also gives ko/en a stable per-row key to keep in parity, rather than a bare array index.
- Playwright's test-file loader cannot evaluate the generated Prisma client module (`SyntaxError: Cannot use 'import.meta' outside a module`) the way Vitest's Vite-native loader can. e2e helpers that need direct DB access for setup/assertions (`e2e/helpers/db.ts`) use `pg`'s `Pool` with raw SQL instead — never import `@/generated/prisma/client` from an e2e file.
- "Sensitive field never reaches role X" (H4: moderators must not see `interestedIn`) is enforced by the shape of the Prisma `select` clause, not by what the UI happens to display — test it by asserting the forbidden key never appears anywhere in the `select`/`include` tree passed to a fake DB, not just by checking the rendered/returned shape looks right; a query that over-selects and a display layer that just doesn't render the field would pass a shape-only test while still leaking the field to anything else that touches that query's result.
- `signIn()` (`e2e/helpers/auth.ts`) waits for the post-verify redirect chain to land (`/onboarding`, `/onboarding/profile`, or `/picks`) before returning, because that chain is async and client-side (LoginForm's `router.push` fires after the fetch resolves). Any caller that does a non-DOM-dependent action right after signing in (a direct DB write, a second `page.goto`) with no intervening wait can otherwise race it and get bounced back mid-chain — this is why the wait lives in the shared helper, not scattered per-test. The same shape of bug hit `e2e/verification.spec.ts`'s reject test even after this fix: it skipped waiting for the *selfie upload's* own async confirmation before immediately having a second browser context query the queue, so under load the queue read could run before the upload's server action had committed. Any auto-submitting upload/action followed by another actor's read needs an explicit wait for that action's own visible success state first.
- This dev database is long-lived across local test runs (unlike CI's fresh ephemeral Postgres per run — see `.github/workflows/ci.yml`), so a queue/list view can hold leftover rows from earlier runs. Don't assert a queue is empty or count its total rows; generate a unique value (e.g. a timestamped name) per test and scope every locator/assertion to the row containing it, the way `e2e/verification.spec.ts` does.
- `a.filter(x => b.includes(x))` is not a safe way to compute a "shared items" set when either array can contain its own duplicates (e.g. a data glitch, or a random test-data generator that repeats a value): swapping which side is `a` vs `b` can change the *count* of a duplicated shared item, silently breaking any code (or property test) that assumes `shared(a,b) === shared(b,a)` (src/server/matching/terms.ts's S10 symmetry property test caught exactly this in its own T-term spot-bonus count). Build "shared" sets via `Set` intersection (`src/server/matching/terms.ts`'s `intersectDeduped`) whenever symmetry or an exact count matters.
- A synthetic-data property test (S10's precision@6 evaluation) can fail for a *reference-data-scale* reason having nothing to do with the algorithm under test: `scripts/generate-synthetic-campus.ts`'s planted communities need enough distinct courses/clubs/interests to give each community a fingerprint the others don't share. With only 25 interest tags (S06's tiny sample dataset) and 20+ communities each drawing 4, cross-community collision is near-total, silently weakening whichever score term leans on interests most (Dating's `wI`/`wV`). Size `--communities` to the actual reference data on hand, not a fixed default, before trusting a low evaluation number as a real regression.
- Any "once per day" job (S11's daily batch; REQUIREMENTS.md also names expiry/reminders/retention-purge as later chunked routes) must compute "today" from the Seoul calendar day, not a UTC-truncated `Date` — Korea is UTC+9 with no DST, so a naive UTC midnight can be up to 9 hours into the wrong day locally. `src/server/matching/seoul-date.ts`'s `seoulCalendarDate()` is the shared way to get this right (via `Intl.DateTimeFormat` with `timeZone: "Asia/Seoul"`, matching `src/server/reference/term.ts`'s existing pattern for the same problem); reuse it rather than re-deriving day boundaries per job.
- A `data-slot="card"` e2e locator only finds what's actually inside the `<Card>` element. Putting a card's action buttons as *siblings* of `<Card>` (rather than inside it, e.g. via `<CardFooter>`) looks fine visually but makes `page.locator('[data-slot="card"]').filter(...).getByRole("button", ...)` silently never find them (S12: `PickCard`'s Pass/Wave buttons). A card's actions belong inside the card (`CardFooter`), not next to it — this is also just the more correct component shape.
- "Stale build/server, not a logic bug" (this file's own existing gotcha about `npm run build`/`npm run start`) applies to `npm run dev` too, specifically for a **brand-new route file**: S12 hit a test that failed consistently against a `next dev` process that had been running since earlier in the session, and passed reliably once restarted, even though dev mode is supposed to hot-reload. If an e2e test for a newly-added page fails in a way that doesn't match the code, restart the dev server before concluding it's a real bug.
- An e2e helper that seeds a *shared* signal between two users by picking from a small reference pool (`e2e/helpers/db.ts`'s `shareCourseAndClub`, e.g., always the same course/club from S06's ~8-row sample dataset) accumulates real "noise" rows in the long-lived local DB across repeated runs — enough of them can crowd a test's own target out of a ranked, capped result (S10's 25-communities-vs-25-interest-tags finding, in this codebase already once; S12 hit it again when 14 leftover users from repeated debugging runs pushed a specific candidate out of the top-6 daily batch entirely). Any e2e test that calls a "force an overlap" helper like this must also clean up the users it creates afterward (`deleteTestUser`) — don't rely on unique naming alone the way tests scoped to an *unbounded* list (`verification.spec.ts`'s queue) safely can.

## Commands

- `npm run dev` starts the app, `npm run check` runs lint, typecheck and unit tests, `npm run e2e` runs Playwright.
- `npm run db:migrate -- --name X` after a schema change, then `npx prisma generate`. `npm run db:seed` for the dev fixture. `npm run db:studio` to browse the database.
- Next.js 16: `src/proxy.ts` replaces `middleware.ts`. Korean is served at `/`, English at `/en`.

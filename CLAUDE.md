# Overlap: campus dating app

Build it step by step from `docs/BUILD_PLAN.md`. The full product spec is `docs/REQUIREMENTS.md`.

## Working protocol

- At the start of a session, read `docs/BUILD_PLAN.md`, find the first unchecked step (`- [ ]`) and do only that step.
- Before coding a step, fetch current docs with Context7 for every library it touches. For Next.js 16 also read the matching guide in `node_modules/next/dist/docs/`.
- A step is done only when every "Done when" check passes. Then tick its box, add a line to the Progress Log in `docs/BUILD_PLAN.md`, and commit as `Sxx: title`.
- Stop at checkpoints C1 to C4 and wait for the owner's review.
- Build only what is in the Month-1 scope map. New ideas go to the Fast-follow list. Split any step that runs past 1.5x its budget.

## Gotchas (learned the hard way)

- Every page and layout calls `setRequestLocale(locale)` before next-intl server APIs so it stays static. `loading.tsx` cannot, so anything it renders that uses next-intl must be a client component, otherwise the whole route becomes dynamic.
- Korean uses system fonts; only the Latin Pretendard slice is self-hosted (`src/app/fonts/README.md`). Do not add the Hangul webfont slices.
- Windows: never `taskkill /IM <image>`, it kills the owner's own programs (this closed their Chrome once). Stop only PIDs you started yourself. If `.next` is locked (`EBUSY`), find what holds it first.
- Lighthouse: set `CHROME_PATH` to Playwright's Chromium and use `C:/...` style paths for Node on Windows.
- Auth is Better Auth (`src/server/auth/auth.ts`), not Supabase Auth — Supabase Auth's default email sending doesn't fit local-only phase (see BUILD_PLAN S05 log for the full reasoning). The `NEXT_PUBLIC_SUPABASE_*`/`SUPABASE_SECRET_KEY` env vars are for Storage (S07 photos), unrelated to auth — and Storage itself follows the same local-only fallback as email (see below), so those vars stay unset until "publish" too.
- Photo/file storage (`src/server/storage/photos.ts`, S07) follows `sendEmail()`'s local-only-phase pattern: real Supabase Storage when `NEXT_PUBLIC_SUPABASE_URL`/`SUPABASE_SECRET_KEY` are set, otherwise a local `.dev-storage/` dir (gitignored) served through a guarded route that 404s once Storage is configured. CI has no Storage credentials either, so this fallback is what CI's own e2e run exercises — treat it as a real code path, not just an offline convenience.
- The `(app)` layout guard (S05, extended in S07 to also require a completed profile) redirects signed-out visitors to `/login`, not-yet-account-onboarded ones to `/onboarding`, and account-onboarded-but-profile-incomplete ones to `/onboarding/profile`. **Adding or changing any guard like this: audit existing e2e tests on the newly-protected routes.** They don't fail loudly — they silently keep "passing" while actually testing the redirect target instead (S05 found `shell.spec.ts`/`a11y.spec.ts` doing exactly this; S07 found it again when the profile-completion guard silently broke `signInAndOnboard()`'s promise to land on `/picks`). Use `signInAndOnboard()` from `e2e/helpers/auth.ts` for tests that need an authenticated, fully-onboarded session (it drives both onboarding stages), and add a `toBe(N)` / `toBeGreaterThan(0)` count guard before any loop over a locator, so an empty match can't pass silently.
- A file with `"use server"` at the top may only export async functions — no plain `const`/object/type-as-value export. This is enforced by the bundler at module-evaluation time, not by `tsc` or `next build`'s type-check step, so a violation compiles clean and only breaks when a page actually renders that module (S07: exporting a step-order lookup object from `src/server/profile/actions.ts` passed every check except real e2e). Put shared constants in a plain (non-`"use server"`) module instead.
- Playwright's `.count()` (and other synchronous-read locator queries) does **not** auto-wait the way `.click()`/`.check()`/`.fill()` do — it reads the DOM immediately. Calling it right after an action that triggers an async transition (a server-action round trip, a step change) can read the *previous* screen's state. Wait for an explicit signal of the new screen first (e.g. `expect(page.getByRole("heading", {...})).toBeVisible()`) before counting or querying (S07's `completeProfileWizard` e2e helper hit this: counting `fieldset`s right after clicking "다음" read 0 from the still-rendering previous step and silently skipped every check).
- Prisma 7 requires a driver adapter for every DB (`@prisma/adapter-pg`) and loads no env file on its own — `prisma.config.ts` loads `.env.local` explicitly. Use `process.env.X` directly there, never `prisma/config`'s `env()` helper: it throws immediately if unset, which breaks `prisma generate` (it needs no DB connection at all) on every clean install, including CI's and Vercel's.
- `prisma migrate dev` does not run `prisma generate` automatically in Prisma 7 — run it explicitly after every schema change or the generated client silently goes stale (wrong fields, confusing type errors). It also refuses to run at all (even with `--create-only`) in a non-interactive shell: use `prisma migrate diff --from-config-datasource --to-schema=prisma/schema.prisma --script` to get the SQL, hand-place it under `prisma/migrations/<timestamp>_name/migration.sql`, then `prisma migrate deploy` to apply and record it.
- No real campus data exists yet (O4). `prisma/seed.ts` creates a dev-only Campus + `test.ac.kr` EmailDomain for local/CI testing; it refuses to run when `NODE_ENV=production`.
- If you edit server code (actions, `sendEmail`, etc.) after already starting `npm run build`/`npm run start`, the running server is still serving the old build — rebuild and restart before trusting any test result. A test that fails for a suspiciously infrastructural reason (missing file, stale behavior) is worth checking against a fresh build before assuming it's a logic bug.
- CI uses its own throwaway `postgres:17-alpine` service (see `.github/workflows/ci.yml`), never the real Seoul database — don't add real DB credentials as GitHub secrets. New required env vars need a matching dummy (non-secret) value added to the CI workflow's `env:` block, or CI breaks even though local `.env.local` works fine.
- The dev/CI shell can have **real Seoul Supabase `DATABASE_URL`/`DIRECT_URL`** ambient in its environment (pointed at `aws-0-ap-northeast-2.pooler.supabase.com`), not just the `NEXT_PUBLIC_SUPABASE_*`/`SUPABASE_SECRET_KEY`/`SUPABASE_JWKS_URL` vars covered above — and since real process env always beats `.env.local`, `npm run dev`/`npm run e2e` silently talk to the real remote pooler instead of the local throwaway Postgres if only the Storage-related vars are unset. This doesn't fail loudly: pages still render, but every DB query (starting with the login OTP request) hangs for a few seconds and then fails with `pg-pool`'s "Connection terminated due to connection timeout" (the remote pooler is unreachable/too slow from here) — which looks exactly like a flaky signed-in e2e test, not an env problem, and can eat a lot of debugging time chasing the wrong cause (S13 lost real time to this before finding it: a plain `node -e` script using a hardcoded local connection string worked instantly, which is what revealed that only the *app's* connection was going elsewhere). For `npm run dev`, unsetting `DATABASE_URL`/`DIRECT_URL` is enough — `next dev` loads `.env.local` itself and fills them back in with the local value. For `npm run e2e`/`npx playwright test`, **export the local value instead of unsetting it** (`export DATABASE_URL=... DIRECT_URL=...`, both `postgresql://postgres:postgres@localhost:5432/postgres` in dev): the Playwright test-runner process itself (not just the `next dev` child it spawns) reads `process.env.DATABASE_URL` directly in `e2e/helpers/db.ts`'s own `pg.Pool`, and unlike `next dev` it does no `.env.local` loading of its own — leaving the var merely unset makes every `db.ts` helper call (`promoteToRole`, `verifyUser`, …) fail with pg's unrelated-looking "no PostgreSQL user name specified in startup packet".
- `src/server/env.ts` validates required env vars up front and is imported by `auth.ts` specifically so a missing `BETTER_AUTH_SECRET` fails the build instead of silently falling back to Better Auth's insecure default (which only warns). Import it from any other module that would otherwise fail unclearly on a missing var.
- A design-token pairing like `text-warning-foreground` is calibrated for a _solid_ `bg-warning`; pairing it with a low-opacity tint (`bg-warning/10`) can fail contrast in dark mode even though light mode looks fine. Use `text-foreground` (or `text-warning` for accents only) on tinted/subtle variants — see `src/components/draft-notice.tsx`.
- **Private Vercel deploy (2026-10-01, project `ras-5e26/overlap`):** `vercel deploy` (no `--prod`) creates a Preview deployment, which Vercel automatically protects with `vercel_authentication` on every plan including Hobby — confirmed by inspecting the deploy result's `deploymentProtection` field and by an anonymous request actually redirecting to `vercel.com/login`. This is what makes the private-deploy exception above workable without a paid plan. Gotchas hit getting there: (1) env vars must be added via the Vercel dashboard, not this agent's CLI — writing to an external secret store is blocked by Claude Code's auto-mode classifier regardless of batching or per-variable retries. (2) `vercel deploy`'s default target was ambiguous for this project's first deploy; pass `--target=preview` explicitly or env resolution silently fails (`env.ts` reports required vars as `undefined` even though the dashboard shows them correctly scoped to Preview). (3) Every CLI deploy gets a brand-new random URL (`overlap-<hash>-ras-5e26.vercel.app`), which breaks `NEXT_PUBLIC_SITE_URL`/`BETTER_AUTH_URL` (baked in at build time) on every redeploy — fixed with a stable alias (`vercel alias set <new-deploy-url> overlap-rahimjon.vercel.app --token=...`) that both those env vars point to instead; **re-run the alias command after every future deploy**, since the alias doesn't move on its own. (4) Vercel's Hobby plan only allows daily cron schedules — `vercel.json`'s `/api/cron/notifications` was hourly (S18) and had to drop to once-daily (`0 6 * * *`) for this deployment specifically; revisit the real cadence if this ever moves to a paid plan for an actual public launch.
- `messages/{ko,en}.json` values are constrained to `string | string[] | Tree` (`src/i18n/messages.test.ts`'s own type, which also asserts ko/en have identical key sets and no empty strings) — an array of objects (e.g. a table's rows as `[{heading, body}, ...]`) fails that type check at `tsc` time, even though `t.raw()` would happily return it at runtime. For structured content (S13's Terms/Privacy sections and tables), use a keyed object of objects instead (`{ purpose: {heading, body}, eligibility: {...} }`) and `Object.values()` it in the page — this also gives ko/en a stable per-row key to keep in parity, rather than a bare array index.
- Playwright's test-file loader cannot evaluate the generated Prisma client module (`SyntaxError: Cannot use 'import.meta' outside a module`) the way Vitest's Vite-native loader can. e2e helpers that need direct DB access for setup/assertions (`e2e/helpers/db.ts`) use `pg`'s `Pool` with raw SQL instead — never import `@/generated/prisma/client` from an e2e file.
- "Sensitive field never reaches role X" (H4: moderators must not see `interestedIn`) is enforced by the shape of the Prisma `select` clause, not by what the UI happens to display — test it by asserting the forbidden key never appears anywhere in the `select`/`include` tree passed to a fake DB, not just by checking the rendered/returned shape looks right; a query that over-selects and a display layer that just doesn't render the field would pass a shape-only test while still leaking the field to anything else that touches that query's result.
- `signIn()` (`e2e/helpers/auth.ts`) waits for the post-verify redirect chain to land (`/onboarding`, `/onboarding/profile`, or `/picks`) before returning, because that chain is async and client-side (LoginForm's `router.push` fires after the fetch resolves). Any caller that does a non-DOM-dependent action right after signing in (a direct DB write, a second `page.goto`) with no intervening wait can otherwise race it and get bounced back mid-chain — this is why the wait lives in the shared helper, not scattered per-test. The same shape of bug hit `e2e/verification.spec.ts`'s reject test even after this fix: it skipped waiting for the *selfie upload's* own async confirmation before immediately having a second browser context query the queue, so under load the queue read could run before the upload's server action had committed. Any auto-submitting upload/action followed by another actor's read needs an explicit wait for that action's own visible success state first.
- This dev database is long-lived across local test runs (unlike CI's fresh ephemeral Postgres per run — see `.github/workflows/ci.yml`), so a queue/list view can hold leftover rows from earlier runs. Don't assert a queue is empty or count its total rows; generate a unique value (e.g. a timestamped name) per test and scope every locator/assertion to the row containing it, the way `e2e/verification.spec.ts` does.
- `a.filter(x => b.includes(x))` is not a safe way to compute a "shared items" set when either array can contain its own duplicates (e.g. a data glitch, or a random test-data generator that repeats a value): swapping which side is `a` vs `b` can change the *count* of a duplicated shared item, silently breaking any code (or property test) that assumes `shared(a,b) === shared(b,a)` (src/server/matching/terms.ts's S10 symmetry property test caught exactly this in its own T-term spot-bonus count). Build "shared" sets via `Set` intersection (`src/server/matching/terms.ts`'s `intersectDeduped`) whenever symmetry or an exact count matters.
- A synthetic-data property test (S10's precision@6 evaluation) can fail for a *reference-data-scale* reason having nothing to do with the algorithm under test: `scripts/generate-synthetic-campus.ts`'s planted communities need enough distinct courses/clubs/interests to give each community a fingerprint the others don't share. With only 25 interest tags (S06's tiny sample dataset) and 20+ communities each drawing 4, cross-community collision is near-total, silently weakening whichever score term leans on interests most (Dating's `wI`/`wV`). Size `--communities` to the actual reference data on hand, not a fixed default, before trusting a low evaluation number as a real regression.
- Any "once per day" job (S11's daily batch; REQUIREMENTS.md also names expiry/reminders/retention-purge as later chunked routes) must compute "today" from the Seoul calendar day, not a UTC-truncated `Date` — Korea is UTC+9 with no DST, so a naive UTC midnight can be up to 9 hours into the wrong day locally. `src/server/matching/seoul-date.ts`'s `seoulCalendarDate()` is the shared way to get this right (via `Intl.DateTimeFormat` with `timeZone: "Asia/Seoul"`, matching `src/server/reference/term.ts`'s existing pattern for the same problem); reuse it rather than re-deriving day boundaries per job.
- A `data-slot="card"` e2e locator only finds what's actually inside the `<Card>` element. Putting a card's action buttons as *siblings* of `<Card>` (rather than inside it, e.g. via `<CardFooter>`) looks fine visually but makes `page.locator('[data-slot="card"]').filter(...).getByRole("button", ...)` silently never find them (S12: `PickCard`'s Pass/Wave buttons). A card's actions belong inside the card (`CardFooter`), not next to it — this is also just the more correct component shape.
- "Stale build/server, not a logic bug" (this file's own existing gotcha about `npm run build`/`npm run start`) applies to `npm run dev` too, specifically for a **brand-new route file**: S12 hit a test that failed consistently against a `next dev` process that had been running since earlier in the session, and passed reliably once restarted, even though dev mode is supposed to hot-reload. If an e2e test for a newly-added page fails in a way that doesn't match the code, restart the dev server before concluding it's a real bug.
- An e2e helper that seeds a *shared* signal between two users by picking from a small reference pool (`e2e/helpers/db.ts`'s `shareCourseAndClub`, e.g., always the same course/club from S06's ~8-row sample dataset) accumulates real "noise" rows in the long-lived local DB across repeated runs — enough of them can crowd a test's own target out of a ranked, capped result (S10's 25-communities-vs-25-interest-tags finding, in this codebase already once; S12 hit it again when 14 leftover users from repeated debugging runs pushed a specific candidate out of the top-6 daily batch entirely). Any e2e test that calls a "force an overlap" helper like this must also clean up the users it creates afterward (`deleteTestUser`) — don't rely on unique naming alone the way tests scoped to an *unbounded* list (`verification.spec.ts`'s queue) safely can. The same crowding shows up *within a single run* too, not just across repeated ones: S15's full-suite run found that `shareCourseAndClub` always picking the exact same "`LIMIT 1`" course/club meant every concurrent test calling it (a11y.spec.ts, picks.spec.ts, waves.spec.ts, chat.spec.ts, several of which run in parallel by design) piled its pair onto the identical row at the same moment, so the pool briefly held far more "equally good" candidates than any one test's own top-6 expects — a `-g`-scoped or isolated re-run of the failing test alone won't reproduce this, since it only shows up when several *different* spec files' shareCourseAndClub calls actually overlap in time. Fixed by having the helper pick a **random** course/club (`ORDER BY random() LIMIT 1`) each call instead of always the same one, which sharply cuts (but with only ~7-8 reference rows, doesn't fully eliminate) the odds of two concurrent tests colliding on the identical row — a residual rare flake in this class is expected and consistent with the sample dataset's small size, not a new regression, the same way the existing sandbox-resource-contention flake below is already treated.
- A heavier two-context e2e test (two full onboardings *plus* extra steps beyond just wave/match formation — S15's chat test adds two message-send-and-poll round trips on top of the mutual-wave flow) can individually run in the ~20-28s range, close enough to Playwright's default 30s per-test timeout that ordinary full-suite resource contention (this file's existing "sandbox resource-contention" gotcha) tips it over, even though the same test passes reliably alone. Rather than shrinking the test or the app's own polling interval (the thing being verified), give that one test explicit headroom with `testInfo.setTimeout(60_000)` — Playwright best practice for a test that's legitimately doing more work than its siblings, not a sign of a real hang.
- Verify **both** Playwright projects (`--project=desktop` and `--project=mobile`). Before 2026-10-04, steps only ever checked desktop. The mobile-only "(signed in) has no horizontal scroll at 360px" failure noted at S16 (a `나중에 할게요` skip button intercepted by a label) no longer reproduces: the full mobile run on 2026-10-04 passed those checks, and its three remaining failures were the same hydration and timing classes fixed for desktop.
- Adding a new *read-time* filter to a query that an existing e2e test already exercises (S16 added a blocked/hidden re-check to `picks/queries.ts`'s `getPicksForActor`, on top of S10's composition-time-only filtering) can invalidate that test's premise, not just its assertion: `waves.spec.ts`'s S14 "blocked user cannot wave" test *reloaded the page after blocking* and asserted the stale card was still visible, deliberately, to isolate the wave action's own defense-in-depth check from the candidate pool's. Once picks started re-filtering on every read, that reload correctly started removing the card — the test needs restructuring (assert the action-level check *before* reloading, then assert the list-level removal *after*), not reverting either side. Whenever a step adds a filter/exclusion to a query, grep existing e2e tests that hit the same query for an assertion about what happens *after* the condition the filter now catches.
- `Intl.DateTimeFormat` for `ko-KR` with `hour: "numeric"` or `timeStyle` can render the AM/PM day-period marker differently between Node's SSR environment and a browser's own ICU data ("오전" server-side vs. plain "AM" client-side, at least in this sandbox's Chromium build) — a real hydration mismatch in any `"use client"` component that formats a date during its own render (S17's `MeetupPlanner`, first hit as `getByText("확정됨")` never appearing because React discarded and re-rendered the whole subtree mid-interaction). Pass `hourCycle: "h23"` explicitly wherever such a formatter runs in a client component to sidestep the day-period marker entirely, rather than trusting the locale's default to agree across environments.
- `e2e/helpers/db.ts`'s `createMatch(emailA, emailB)` returns its newly-created **Conversation's** id, not the `Match` row's own id (S14/S15 only ever needed the conversation id for their own tests) — a new test that actually needs the match id itself (S17's meetup planner, keyed by `matchId`) must look it up separately via the new `getMatchId(emailA, emailB)` helper; assigning `createMatch`'s return value to a variable named `matchId` compiles fine but silently queries the wrong table.
- A server action's *first-ever* hit in a given `next dev` process can push its own round trip (POST the action, then a client-triggered `router.refresh()` re-fetch) past Playwright's default 5s per-assertion timeout purely from Turbopack's on-demand compile of that code path — distinct from this file's existing "stale build" and "heavier whole-test" timeout gotchas, this is a *per-assertion* cold-start cost on an otherwise-fast action (S17's meetup accept/decline actions). Confirmed by re-running the same test immediately after in the same process, where it passes near-instantly. Give the specific assertion right after that first click extra headroom (e.g. `{ timeout: 15_000 }`) rather than bumping the whole test's timeout or suspecting the action's logic.
- No per-user language preference exists anywhere in the schema (S18: checked `User`/`Profile` before building `Notification`) — locale has only ever been a routing concern (`src/i18n/routing.ts`: ko at `/`, en at `/en`), and the OTP/waitlist emails that predate S18 are English-only with no locale awareness at all. S18's ko/en notification templates (`src/server/notifications/templates.ts`) are real, tested in both languages, but every `Notification` row defaults its own `locale` column to `"ko"` (the app's own default locale) rather than trying to infer or ask for one — adding real per-user language selection is its own feature, out of S18's scope, and should get its own step if it's ever needed rather than being smuggled into a template file.
- A cron-triggered background job (S11's daily batch, S15's chat lifecycle, now S18's notification queue) is verified with unit tests that inject `now`/`sendEmail` and, separately, a manual run of its CLI script (`scripts/run-*.ts`) — never a Playwright e2e test of the cron route itself. Controlling real wall-clock time (quiet hours, "silent for 72h", "unread for 1h") from inside a browser-driven e2e test isn't practical, so don't try to force one; a Vitest test using the *real* `sendEmail()` against the real `.dev-outbox.jsonl` (via `e2e/helpers/dev-outbox.ts`'s `readLastEmail`, safely importable from a Vitest file since it has no Prisma-client import) is what actually proves the local-only-phase send path end to end for this class of feature — see `src/server/notifications/queue.test.ts`.
- S18's "queued, not dropped" quiet-hours rule is implemented as two separate steps, never one: every trigger (`formMatch`, `sendWave`, the unread-message finder) only ever inserts a `QUEUED` `Notification` row via `enqueueNotification`'s idempotent upsert; a completely separate job (`processQueuedNotifications`, run hourly via `/api/cron/notifications`) is the only thing that ever sends one, and during quiet hours (21:00-08:00 Seoul, `isSeoulQuietHours`) it does nothing at all rather than attempting-then-requeuing. A trigger site must never call `sendEmail()` directly for a match/wave/unread-message notification — that would bypass quiet hours entirely.
- Prisma 7 rejects a plain `null` when writing to a nullable `Json?` column (`updateMany({ data: { evidence: null } })` fails `tsc` with "Type 'null' is not assignable to type 'NullableJsonNullValueInput | InputJsonValue | undefined'") — use `Prisma.DbNull` (from `@/generated/prisma/client`'s `Prisma` namespace) to actually set the column to SQL `NULL`; `Prisma.JsonNull` is for a different thing (storing the JSON value `null` inside a non-null column) and doesn't fix this. First hit: S19's `purgeReportEvidence` nulling `Report.evidence`.
- S19's account-deletion flow (30-day grace, §15.4) is deliberately two-phase, matching the same "queue now, act later" shape as S18's notifications: `requestAccountDeletion` (self-service, immediate) only ever flips `User.status` to `DELETED` and stamps `deletedAt` — it never touches PII. The actual scrub (email → a synthetic `deleted-<id>@purged.invalid` placeholder since the column is unique/NOT NULL, name/image/birthYear/ageVerifiedAt → null, `Profile` row deleted outright) happens only in `purgeDeletedAccounts`, 30 days later, and only ever nulls/deletes the identifying part — the `User` row itself is never deleted, since Waves/Matches/Messages/Reports still reference it (same "null the sensitive part, keep the row" shape as `purgeSelfies`/`purgeReportEvidence`). Don't shortcut this into a single-phase delete even for a "just get it done" fix — the grace period is the whole point of the retention rule.
- Building a "give the user all of their own data" export via one nested `prisma.user.findUnique({ where: { id: userId }, select: {...deep relations...} })` (`src/server/privacy/export.ts`'s `buildUserDataExport`, S19) is the safest shape for a "this user's data and nobody else's" guarantee: every returned row is structurally reachable only via that one user's own relations, so there's no separate join/filter condition elsewhere in the function that a future edit could accidentally widen. Keep new per-model queries for this kind of "all of X's data" feature nested under a single root `findUnique`, not as N separate top-level queries joined by `userId` — the latter is exactly the shape that's one dropped `where` clause away from leaking another user's row.
- A `router.refresh()`-driven server-action assertion (already documented for S17's first-hit-in-a-fresh-process case) can also fail well past even a bumped `{ timeout: 15_000 }` when several *other* two-context e2e tests are deliberately run alongside it under `--workers=2+` — S19's consent-withdrawal test failed this way in a hand-crafted heavy combination (3 two-context spec files, `workers=2`) but passed cleanly, repeatedly, both alone and in the actual default full-suite run (`fullyParallel`, default worker count). Don't chase a failure that only reproduces under an artificially heavier combination than the real suite ever runs — confirm against a real default `npx playwright test --project=desktop` run (the same bar every prior step's verification has used), not a manually escalated stress test.
- **Path traversal via Next's catch-all route matcher, decode-order bug (S20, HIGH severity, found by the `security-review` skill):** a catch-all segment (`[...segments]`) is not safe to validate with a per-segment `segment === ".."` check. Next's route matcher (`node_modules/next/dist/shared/lib/router/utils/route-matcher.js`) does `match.split('/').map(decode)` — it splits the *raw, still percent-encoded* pathname on literal `/` first, and only decodes each piece afterward. An encoded slash inside what looks like one segment (`..%2F..%2Fsecret.txt`) is never split, so it survives as a single un-split segment whose *decoded* value contains embedded `/` and `..` — which will never equal the literal string `".."`, so it sails straight through a naive per-segment check. `src/app/api/dev-storage/[...segments]/route.ts` had exactly this bug. Fixed at the load-bearing layer in `src/server/storage/blob.ts`'s `devStoragePath()`: resolve the joined key against the bucket root with `path.resolve` and reject anything that doesn't stay under that root as a prefix — never trust a per-segment string check on any catch-all route that builds a filesystem or storage path from it.
- `next.config.ts`'s `experimental.serverActions.bodySizeLimit` defaults to 1MB — smaller than this app's own `MAX_PHOTO_BYTES`/`MAX_SELFIE_BYTES` (8MB) checks inside `addPhoto`/`submitSelfie`. A real phone photo (often 3-10MB before `sharp` resizes it) between 1-8MB would be silently rejected by the framework before ever reaching the app's own size check — masked entirely in e2e because every fixture (`e2e/fixtures/*.jpg`) is only a few KB. Set `bodySizeLimit` to match the app's own stated max whenever one changes (S20 set it to `"8mb"`).
- Rate-limiting a server action against abuse (S20: waves, messages, reports, photo/selfie uploads) reuses S04's OTP `checkRateLimit(prisma, key, {max, windowMs})` primitive with a per-action key prefixed by `actor.userId` — this is a distinct concern from a business-rule cap like the 8/day wave send cap (`DAILY_WAVE_CAP`) and both can coexist on the same action. Following established e2e precedent (no prior step, including S04's own OTP limit, ever added a Playwright test to trip a rate limit), verify these with unit tests on `checkRateLimit` only, not a new e2e test per action.
- A logging chokepoint that scrubs sensitive fields (`src/server/logging.ts`'s `captureError`, S20, the wiring point a real Sentry SDK would plug into once "publish" lifts local-only phase) must scrub only the *extra context* object, never an `Error`'s own `.message`/`.stack` — `scrub.ts`'s `DEFAULT_SENSITIVE_KEYS` includes the literal key `"message"` (meant to catch a chat-Message-row-shaped payload), which would incorrectly redact every ordinary diagnostic error message if the whole error were scrubbed as one shape.
- A module-level `const FOO_PATH = path.join(process.cwd(), "...")` binds to whatever `process.cwd()` is at *import* time, not at call time — harmless for a path used only from the real app process (`sendEmail()`'s `DEV_OUTBOX_PATH`, always run from the repo root), but wrong for anything a unit test exercises via the `mkdtemp`/`process.chdir()` isolation pattern (`blob.test.ts`'s established convention): the module is typically imported once, before any test's `beforeEach` first `chdir()`s, so every call silently reads/writes the *real* repo directory instead of the test's scratch dir. `src/server/storage/blob.ts`'s `devStoragePath()` already gets this right (recomputes `process.cwd()` per call, per its own comment) — S21's `src/server/ops/alerts.ts` first shipped the module-level-constant version, which looked fine running its own test file in isolation once, but was actually reading/writing the real repo's `.dev-alerts.jsonl` the whole time (bound to whatever cwd the test runner's process had at import, before any test's `chdir()` ran); repeated manual runs during the same session kept appending to that one real file, so a later run's "starts empty" test failed with several leftover entries from earlier runs instead of zero. Any new file-backed dev-only store must recompute its path inside each exported function, never cache it in a top-level constant.

- **Fast-follow realtime chat (2026-10-01):** `page.waitForLoadState("networkidle")` never resolves on any page holding an open WebSocket (the chat thread's realtime subscription, `src/components/chat/chat-thread.tsx`) — "networkidle" means no network activity for 500ms, which a persistent connection never provides. `e2e/a11y.spec.ts`'s shared `assertNoViolations` helper used it generically across every route; switched to `waitForLoadState("load")`, which matches the actual intent (let the initial page settle) without depending on network silence. Also needed `next.config.ts`'s CSP `connect-src` opened to `https://*.supabase.co wss://*.supabase.co` (previously bare `'self'`) — the browser-to-Realtime WebSocket is the app's first ever browser-to-Supabase connection (Storage only ever calls Supabase from the server), and a CSP block surfaces as a generic `CHANNEL_ERROR: transport failure` from realtime-js with nothing resembling a CSP violation in sight. Server-side broadcasting uses `channel.httpSend(event, payload)`, not `channel.send({type:"broadcast",...})` — the server never subscribes (it only ever publishes), and plain `send()` without a subscription silently falls back to this same REST path with a deprecation warning anyway.
- **This real Seoul database had 13 migrations (S06-S19) applied for the first time only on 2026-10-01** — the cloud session that built those steps must have developed against a different database, since `prisma migrate status` showed them as pending here despite the code (and its own BUILD_PLAN log entries) assuming they'd long been live. Applying old pending migrations to a long-lived real database is routine (`prisma migrate deploy`), but it also meant **`interests.csv`/`prompts.csv` had never been imported either** (only `prisma/seed.ts`'s Campus/EmailDomain had run) — the profile wizard's prompt/interest pickers silently had zero options, which looked like a UI bug but was a missing-reference-data problem (`npm run db:import-reference -- --dir reference-data/shared --domain test.ac.kr` fixes it; the shared lists moved out of `sample/` into `shared/` on 2026-10-04) — and that **no Supabase Storage buckets existed at all** (`profile-photos`, `verification-selfies`), created directly via `insert into storage.buckets` since no dedicated creation tool was available; the app's own upload code otherwise works unmodified since it always uses the service-role key, which bypasses bucket-level RLS. Before trusting any "this feature doesn't work" finding against a database you didn't personally set up end-to-end, check `prisma migrate status`, whether the shared reference-data import has ever run, and whether the Storage buckets it depends on exist.
- **Selfie upload race, fixed (2026-10-02):** `/verify`'s file input is server-rendered and visible before React hydrates, so `setInputFiles` ran before its `onChange` existed and the upload silently never started (the server action was never called). The verification e2e tests now call `waitForHydration()` (`e2e/helpers/hydration.ts`), which waits for React's `__reactProps` key on the input. A visibility check can't prove hydration, and a fixed sleep only hid the race. Separately, the first hit of `/onboarding/profile` in a fresh dev server can take about 4s to redirect, so `completeProfileWizard` allows 15s for that URL change instead of the default 5s.

- **Never call `router.refresh()`/`router.push()` while rendering (fixed 2026-10-04).** The "adjust state during render" pattern (`if (state !== last) { setLast(state); ... }`) is fine for local `setState`, but a Router update from inside another component's render is rejected by React ("Cannot update a component (`Router`) while rendering a different component"), and the refresh is silently dropped: the server action succeeds, the screen stays stale. This pattern had spread to 16 components. Use `useRefreshOnSuccess(state)` (`src/hooks/use-refresh-on-success.ts`) instead. `login-form.tsx`'s render-phase `router.push` has the same warning but still navigates; it's left as-is for now.
- **E2E hydration and two-user races (2026-10-04):** a server-rendered button is visible before React attaches its handler, and a click on it then is silently dropped. Navigate with `gotoHydrated()` and click action buttons inside nested client components with `clickHydrated()` (`e2e/helpers/hydration.ts`). When user B acts and user A then reads, wait for B's own success state first (meetup decline, `/plan` proposal). The suite default timeout is 90s because onboarding uploads three photos to real Supabase Storage (~15-20s per user).
- `ensureTodaysBatchForUser` is check-then-insert, so two concurrent `/picks` renders can race on the `(userId, intent, batchDate)` unique key. `persistBatch` treats that P2002 as success (fixed 2026-10-04); keep any new "create today's X if missing" path idempotent the same way.

- **Cohort release (S26 prep, 2026-10-04)** is behind `COHORT_RELEASE=on`, off by default. "Can this user use Dating?" has one answer, `getDatingStatus()` (`src/server/cohorts/release.ts`): `needs_consent` (the user's choice), `cohort_closed` (the launch's density gate), or `available`. Storing "who I'd like to meet" stays consent-only (`canUseDatingMode`), so a closed cohort can still fill it in ahead of time. `e2e/cohort-release.spec.ts` skips itself unless the flag is on, and it needs a fresh server started with the flag (`reuseExistingServer` would pick up one without it). Launch steps: `docs/deploy-runbook.md` (S24), `docs/go-no-go.md` (S25), `docs/launch-runbook.md` (S26).
- **Since 2026-10-04 `.env.local` itself points at the real Seoul pooler** (there is no local Postgres on this machine), so e2e runs and migrations hit the remote database. Run Playwright with `--workers=1`: two workers exhaust pooler connections and fail ~50 tests with "No OTP code found in dev outbox" or pg connection timeouts. Don't edit app source during an e2e run (hot reload breaks the run), and kill any `next dev` PID the run leaves behind, since `reuseExistingServer` would pick it up next time. The database now holds more than one campus (Gachon plus the dev placeholder), so any e2e helper that picks reference rows must scope them to the user's own campus (`shareCourseAndClub` does).
- Web push (Month-2 #7) follows the `sendEmail()` switch: with `VAPID_PRIVATE_KEY` unset, `sendPush()` only appends to `.dev-push.jsonl`. Never set the private key before "publish": it turns on real delivery through browser vendors' push services. Headless Chromium reports `Notification.permission` as "denied" even after `context.grantPermissions(["notifications"])` and can't reach a push service, so `e2e/push.spec.ts` stubs the permission and `PushManager.subscribe` in an init script and keeps everything else real.
- Better Auth user ids are 32-character alphanumeric strings, not UUIDs. Validate them with `z.string().min(1).max(64)`, never `z.uuid()`; only Prisma-generated ids (events, courses, clubs, spots) are UUIDs.
